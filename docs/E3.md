**Status:** **Deployed and tested** 2026-10-31 (happy, fail, and idempotent retry on the live API)

## Goal

Expose the frozen **E2 RAG pipeline** behind a **thin AWS HTTP API** with **DynamoDB-backed idempotency**. Duplicate client submits with the same idempotency key must return the cached result without a second LLM call.

This slice answers: *Do I want to own the production glue around LLM calls — APIs, state, retries — the way I've owned middleware and orchestration before?*

Complements E1 (tool orchestration) and E2 (grounded retrieval). E3 is **platforms, not notebooks**. See [LLM inference fit](concepts/llm-inference-fit.md), [Idempotency key](concepts/e3/idempotency-key.md).

## Stack (locked for E3)

| Choice | Lock |
|--------|------|
| Wrap target | **E2 only** — import `e2.rag.answer_query`; do not reopen E1/E2 logic |

| State | **DynamoDB** — partition key `idempotency_key`; store serialized E2 result |
| IaC | **SAM** (default) — CDK acceptable only if developer already prefers it |

Optional stretch (only if core paths freeze early): one **transient LLM retry** inside Lambda (single backoff) for xAI errors — not required for done.

## Architecture (conceptual)

```text
Client
  POST /ask  { "query": "...", "idempotency_key": "..." }
       │
       ▼
  API Gateway (HTTP API)
       │
       ▼
  Lambda handler
       ├─ idempotency_key in DynamoDB? → return cached JSON (log: cache_hit)
       ├─ else → answer_query(query) from e2.rag
       ├─ persist result + key in DynamoDB
       └─ return JSON (same shape as E2 CLI output, plus cache metadata if useful)

Logs must distinguish cache hit vs LLM invocation (CloudWatch line is enough).
```

E2 corpus ships inside the Lambda deployment package (markdown under `e2/corpus/`).

## API contract (v1)

See [Idempotency key](concepts/e3/idempotency-key.md) for why the client sends this field and how E3 stores retries.

**Request** — `POST /ask`

```json
{
  "query": "Is SMS allowed for residential Northeast active segments?",
  "idempotency_key": "demo-happy-001"
}
```

**Response** — same core fields as E2 CLI:

```json
{
  "query": "...",
  "answer": "...",
  "citations": [ { "doc_id": "...", "path": "...", "score": 2.0, "excerpt": "..." } ],
  "status": "answered",
  "retrieval": { "method": "lexical", "hit_count": 1, "min_score": 2.0 },
  "cache": { "hit": false }
}
```

Validation errors (missing `query` or `idempotency_key`) → `400` with structured error body.

## Scenarios

### Happy path

**Input:** In-corpus question (same as E2 happy), new idempotency key.

**Expected:**

1. API returns `status: "answered"` with at least one citation.
2. `cache.hit` is `false` on first request.
3. CloudWatch shows LLM path (not cache hit).

### Fail path

**Input:** Out-of-corpus question (same as E2 fail), new idempotency key.

**Expected:**

1. API returns `status: "unknown"`.
2. No invented policy or facts; citations empty or minimal per E2 behavior.
3. Result is still **cached** under the idempotency key (unknown is a valid cached outcome).

### Idempotent retry path (required)

**Input:** Repeat the **same** request body (same `idempotency_key` and `query`) as happy path.

**Expected:**

1. Identical JSON response to the first call.
2. `cache.hit` is `true` (or equivalent log proves no second LLM call).
3. CloudWatch shows cache hit — **no second xAI invocation**.

Run via curl against deployed API (preferred) or documented local invoke with DynamoDB (local or real table).

**Bruno collection:** [bruno/p5-e3/](../bruno/p5-e3/) — open in [Bruno](https://www.usebruno.com/). `ASK_API_URL` supplies `baseUrl`; see [how-to/bruno-e3.md](how-to/bruno-e3.md).

## Pipeline (conceptual)

```text
HTTP POST
  → validate body
  → DynamoDB get(idempotency_key)
  → if hit → return cached
  → else answer_query(query)
  → DynamoDB put(idempotency_key, result)
  → return JSON
```

Prefer a **single synchronous endpoint** over async job polling for v1.

## Done definition

E3 is **frozen** when all of the following are true:

1. **Deployable SAM stack** (or equivalent) creates API + Lambda + DynamoDB table.
2. Happy path works end-to-end against deployed API (or documented local parity).
3. Fail path returns `status: "unknown"` without inventing facts.
4. Idempotent retry path returns cached result with evidence of **one** LLM call total.
5. [docs/how-to/setup-run-deploy.md](how-to/setup-run-deploy.md) documents deploy, env/secrets, and curl examples for all three paths.
6. No secrets committed; E1/E2 remain unchanged except imports/packaging needed for Lambda.
7. [P5_CHARTER.md](../P5_CHARTER.md) status updated; freeze note recorded.

## How to use this with the next LLM

1. **E1 and E2 stay frozen.** E3 imports `answer_query`; do not refactor RAG or the agent.
2. **E3 is deployed and tested.** Do not reopen it unless asked.
3. Stay anonymous in `docs/`, README, code, IaC comments.
4. Prefer thin SAM tracer over production-grade platform rebuild.
5. Real AWS deploy preferred; local-only is fallback if account access blocks deploy.
