## Goal

Build a minimal **LangChain + xAI** agent that takes a campaign brief and [segment](concepts/marketing/segments.md) stub, calls stub tools in a sensible order, and returns a **structured journey proposal** plus a **constraint validation result**.

Marketing defines briefs and audiences in business terms; engineering builds the platform tools agents call — see [Platform vs marketing ops](concepts/marketing/platform-vs-marketing-ops.md). E1 proposes **one journey step** only; production journeys are usually **multi-step graphs** — see [Journey graphs](concepts/marketing/journey-graphs.md). **When LLM inference is appropriate** for this problem shape (and where E1 is a shortcut): [LLM inference fit](concepts/llm-inference-fit.md). Message types: [LangChain message types](concepts/langchain/message-types.md). E1 stubs the platform layer only.

This slice answers: *Does tool-orchestrated workflow automation feel like work I want to do?*

## Scenario

### Happy path

**Input**

- Campaign brief: promote a new fiber upgrade to existing residential customers in the Northeast.
- Segment ID: `seg_residential_northeast_active` — see [Audience segments](concepts/marketing/segments.md)

**Expected agent behavior**

1. Resolve segment metadata (`get_segment`).
2. Fetch audience/compliance rules for that segment (`get_audience_rules`).
3. Propose one journey step — channel, message theme, timing (`propose_journey_step`).
4. Validate the proposal against rules (`validate_constraints`).
5. Return structured JSON with `status: "approved"`.

### Failure path (required demo)

**Input**

- Same brief, segment ID: `seg_residential_northeast_active`
- Agent (or harness) proposes a journey step that includes **SMS** for a segment where SMS is disallowed.

**Expected**

- `validate_constraints` returns violations.
- Final output: `status: "rejected"` with cited rule IDs and reasons.

Run both paths from the CLI (two fixed fixtures or flags).

## Stub tools (4)

All tools are in-process fakes — no external APIs.

| Tool | Purpose | Key inputs | Returns |
|------|---------|------------|---------|
| `get_segment` | Segment metadata | `segment_id: str` | `{ id, name, channel_policy, attributes }` |
| `get_audience_rules` | Compliance / eligibility rules | `segment_id: str` | `{ rules: [{ rule_id, description, constraint }] }` |
| `propose_journey_step` | Draft one journey step | `brief: str`, `segment_id: str`, optional hints | `{ channel, message_theme, timing, rationale }` |
| `validate_constraints` | Check proposal vs rules | `segment_id: str`, `proposal: dict` | `{ approved: bool, violations: [{ rule_id, reason }] }` |

**Fake data notes**

- `seg_residential_northeast_active`: email + in-app allowed; **SMS disallowed** (`rule_no_sms_residential`).
- Rules live in code or a small JSON fixture under `e1/fixtures/`.

The LLM orchestrates tool calls; tools return deterministic data. `propose_journey_step` may be LLM-assisted or a stub that returns a fixed shape — prefer **LLM proposes, tools validate** for the role signal.

## Done definition

E1 is **frozen** when all of the following are true:

1. **Runnable CLI** loads `XAI_API_KEY` from env and runs the happy-path fixture end-to-end.
2. **Agent invokes multiple tools** (visible in logs or LangChain trace) — not a single hard-coded script pretending to be an agent.
3. **Structured JSON output** printed to stdout with at least:
   - `segment_id`
   - `proposal` (channel, message_theme, timing)
   - `validation` (approved, violations)
   - `status` (`approved` | `rejected`)
4. **Failure path** demonstrates constraint rejection with at least one cited `rule_id`.
5. **README snippet** or inline `--help` documents how to run both paths.
6. No secrets committed.
